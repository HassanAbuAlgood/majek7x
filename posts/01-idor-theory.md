# 5️⃣ تشريح الـ IDOR — الفهم العميق

> هنا بنتحوّل من "واحد سمع عن IDOR" إلى "واحد بيفهمه كأنه كتبه بإيده".

---

## 📐 التعريف الدقيق

**IDOR** = Insecure Direct Object Reference

بيحصل لما:
1. التطبيق يستقبل **مرجعًا لكائن** (object reference) من المستخدم، و
2. يستخدمه للوصول للكائن **دون التحقق** إن المستخدم يملكه / مخول له.

```
                    ┌─────────────────────────────┐
   request          │  /api/invoices/8821         │
   ───────────────► │  1. هات الفاتورة 8821 ✅    │
                    │  2. مين صاحبها؟  ❌ ← هنا   │
                    │  3. رجّع البيانات ✅         │
                    └─────────────────────────────┘
                                 │
                                 ▼
                          🔴 IDOR — تسريب فاتورة شركة تانية
```

**الاسم الرسمي الحديث**: `BOLA` — Broken Object Level Authorization (OWASP API Security Top 10 — **API1:2023**، المركز الأول).

### ليه المركز الأول؟
لأنه:
- منتشر جدًا (أتمتة الـ frameworks مش بتحميه تلقائيًا)
- سهل الاستغلال (مفيش payloads معقدة)
- تأثيره عالي (بيانات حقيقية لحسابات حقيقية)
- صعب يُكتشف آليًا (الـ scanners مش بتعرف "مين المفروض يوصل لإيه")

---

## 🧩 المعادلة

```
IDOR = (معرّف كائن يتحكم فيه المستخدم)  ×  (غياب فحص الملكية على السيرفر)
```

لو أي عامل منهم = صفر → مفيش ثغرة:
- لو التطبيق بيجيب الـ ID من الجلسة مش من الطلب → مفيش IDOR
- لو بيفحص الملكية صح → مفيش IDOR

**وده بيقولك إيه؟** إن أكتر تطبيق محمي هو اللي مابيثقش في أي معرّف جاي من العميل.

---

## 🎭 أنواع الـ IDOR (حسب التأثير)

### 1. Read IDOR — قراءة
```http
GET /api/v1/users/1337/profile HTTP/1.1
Authorization: Bearer <token_A>
→ 200 OK  { "email": "victim@corp.com", "phone": "...", "ssn": "..." }
```
- **التأثير**: تسريب بيانات
- **السيفيريتي**: Medium → High (حسب حساسية البيانات)
- **الأكثر شيوعًا** والأسهل إيجادًا

### 2. Write IDOR — تعديل 👈 الأهم
```http
PATCH /api/v1/users/1337 HTTP/1.1
Authorization: Bearer <token_A>
{"email": "attacker@evil.com"}
→ 200 OK
```
- **التأثير**: تعديل بيانات الضحية
- **السيفيريتي**: High
- ⭐ لو عدّلت **الإيميل أو رقم الهاتف** → غالبًا تقدر تعمل **Password Reset** → **Account Takeover** → **Critical**

### 3. Delete IDOR — حذف
```http
DELETE /api/v1/documents/8821 HTTP/1.1
→ 204 No Content
```
- **التأثير**: تدمير بيانات
- **السيفيريتي**: High
- ⚠️ **متعملش ده على هدف حقيقي**. اكتفي بإثبات الـ `204` على كائن **بتاعك أنت**
  أو وثّقه في التقرير مع أقوى دليل ممكن بدون تنفيذ فعلي.

### 4. Create-in-other-tenant IDOR
```http
POST /api/v1/teams/{victim_team_id}/invites HTTP/1.1
{"email": "attacker@evil.com", "role": "admin"}
```
- بتنشئ كائن داخل نطاق مستخدم تاني (دعوة، مشروع، طلب)
- غالبًا = **Privilege Escalation** حقيقي

### 5. Function-level (BFLA) — أخو الـ IDOR
```http
GET /api/v1/admin/users HTTP/1.1
Authorization: Bearer <token_مستخدم_عادي>
→ 200 OK
```
- مش IDOR بالمعنى الدقيق (مفيش معرّف كائن)، بس نفس العائلة
- الاسم: **Broken Function Level Authorization** (`API5:2023`)
- دايمًا جرّب الـ `/admin`, `/internal`, `/management`, `/ops` paths

## 🔗 السلاسل (Chains) — إزاي توصل من Medium لـ Critical

الـ IDOR لوحده غالبًا Medium. اللي بيفرق = **إيه اللي تقدر تعمله بعده**.

```
Read IDOR على profile الضحية
   └─► لقيت إيميلها + رقم هاتفها
        └─► Write IDOR على نفس الـ endpoint
             └─► غيّرت الإيميل بتاعها لإيميلك
                  └─► "Forgot password" بالإيميل الجديد
                       └─► ✅ Account Takeover = Critical
```

### سلاسل تانية شائعة

| السلسلة | النتيجة |
|---|---|
| IDOR على API key endpoint | قراءة مفتاح API للشركة = كل بياناتها |
| IDOR على invoice | بيانات مالية لكل العملاء |
| IDOR على invite/team + Mass assignment `role:admin` | تحكم كامل في tenant الضحية |
| IDOR + XSS | XSS في صفحة بيرجّعها IDOR |
| JWT ضعيف (`alg:none`) + IDOR | انتحال شخصية أي مستخدم |
| IDOR على export/report | تنزيل قاعدة بيانات كاملة |

> 💡 **قاعدة البيع**: في التقرير، متكتبش "لقيت IDOR".
> اكتب: **"أي مستخدم موثّق يقدر يقرأ/يعدّل بيانات كل مستخدمي المنصة (X مليون حساب)"**.
> نفس الثغرة، تأثير مختلف تمامًا في التقييم.

## 💰 اقتصاديات الـ IDOR (إزاي يُسعّر)

| العامل | تأثيره على المبلغ |
|---|---|
| Read vs Write/Delete | Write = 2-3× |
| عدد المستخدمين المتأثرين | كل المستخدمين = أعلى |
| نوع البيانات (PII / مالي / أسرار) | الأسرار والمالي أعلى |
| سهولة الاستغلال (مفيش تفاعل ضحية) | أعلى |
| هل يوصل لـ ATO؟ | يقفز لـ Critical |

**نطاقات واقعية** (تختلف جدًا حسب البرنامج):
- Read IDOR لبيانات عادية: `$150 - $800`
- Read IDOR لـ PII حساس: `$500 - $2,500`
- Write/Delete IDOR: `$1,000 - $5,000`
- IDOR → ATO: `$2,500 - $15,000+`

## 🧠 ليش الـ IDOR بيحصل أصلًا؟ (افهم عقلية المطور)

ودي أهم فقرة في الملف — لما تفهم **ليه** هتعرف **فين** تدور:

1. **الثقة في العميل**: المطور فاكر إن العميل مش هيبدّل الـ ID "لأن الـ UI مش هيسمح"
   ← الـ UI مش حماية، الطلب هو الحقيقة
2. **ORM بيخليه سهل**: `Invoice.objects.get(id=request.id)` — سطر واحد، مافيهوش فحص ملكية
3. **UUID بيوهم بالأمان**: "مفيش حد هيخمّن UUID" ← بس الـ IDs بتتسرب في أماكن تانية
4. **الفحص في مكان والاستخدام في مكان**: حماية على `GET` بس، ونسيان `PATCH`
5. **إعادة استخدام الكود**: endpoint قديم كان داخلي وبقى خارجي
6. **مفيش اختبارات أمنية**: الـ unit tests بتفحص "هل بيرجّع البيانات؟" مش "لمن؟"
7. **تعدد الفرق**: فريق الـ API وفريق الـ Web each يفتكر التاني بيفحص

> 🎯 **الخلاصة العملية**: دور على الـ **التناقضات**:
> endpoint محمي وendpoint مش محمي على نفس الكائن،
> method محمية وتانية لأ،
> معرّف بيتفحص في مكان وبيتجاهل في مكان.

---

## ✅ اختبر نفسك

1. عرّف IDOR بمعادلة من سطر واحد.
2. إيه الفرق بين BOLA و BFLA؟
3. ليه الـ Write IDOR أخطر من الـ Read؟
4. اذكر 3 أسباب برمجية بتخلي الـ IDOR يحصل.
5. إزاي تحوّل Read IDOR لـ Critical؟
