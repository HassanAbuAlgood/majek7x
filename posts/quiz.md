## 📗 المرحلة 1 — الأساس (بعد أسبوع 4)

### HTTP والجلسات
1. إيه الفرق بين `401` و `403`؟ وأيهما أدق للبحث عن IDOR؟
2. لو `GET /api/users/1234` → `403` و `GET /api/users/999999` → `404`، إيه الاستنتاج؟
3. إيه الـ Headers اللي ممكن تستخدمها لتخطي الـ 403؟ اذكر 3.
4. إزاي تقرا محتوى JWT؟
5. إيه فايدة `HttpOnly` و `SameSite`؟

### المصادقة والصلاحيات
6. اشرح الفرق بين Authentication و Authorization في جملتين.
7. إيه الفرق بين Horizontal و Vertical privilege escalation؟
8. ليه RBAC لوحده مش كافي لمنع IDOR؟
9. اذكر 3 ثغرات JWT كلاسيكية.
10. إيه الـ multi-tenancy وليه بيهم الـ IDOR؟

### الـ APIs والمعرّفات
11. اذكر 6 أماكن ممكن يختبئ فيها الـ object ID.
12. هل UUID غير القابل للتخمين حماية كافية؟ ليه؟
13. إيه الـ Mass Assignment؟ وإزاي تعرف أسماء الحقول المخفية؟
14. MongoDB ObjectId بيتكوّن من إيه؟
15. إيه فايدة GraphQL Introspection للمهاجم؟

<details>
<summary>👈 الإجابات (متفتحش غير بعد ما تجاوب)</summary>

1. `401` = مش معرّف الهوية. `403` = معرّف بس ممنوع. **`403` أدق** لأنه بيأكد وجود الكائن.
2. الكائن `1234` **موجود فعلًا** لكن الوصول مرفوض ← الكائن حقيقي، واصل البحث عن طريقة تخطي.
3. `X-Original-URL`, `X-Rewrite-URL`, `X-Forwarded-For`.
4. فكّ الجزء التاني (payload) بـ base64، أو على jwt.io.
5. `HttpOnly` = JS مش يقدر يقراها (حماية من سرقة الجلسة بـ XSS). `SameSite` = حماية CSRF.
6. AuthN = "إنت مين؟" (مرة واحدة). AuthZ = "تقدر تعمل إيه؟" (**مع كل طلب**).
7. Horizontal = نفس المستوى، مستخدم تاني. Vertical = صعود لمستوى أعلى (أخطر).
8. RBAC بيفحص **الدور** فقط، مش **الملكية**. `role=user` مش معناه أوصل لبيانات زميلي.
9. `alg:none`, عدم التحقق من التوقيع, key confusion RS256→HS256, `kid` injection.
10. فصل بيانات الشركات عن بعض. لو فُقد فحص الـ `tenant_id` → تسريب بيانات شركة كاملة.
11. path, query, body (JSON/XML/form), header, cookie, JWT claim, GraphQL variable.
12. **لا**. المعرّف بيتسرب في أماكن تانية (ردود تانية، JS، أرشيف، قوايم، export).
13. ربط كل حقل في الطلب بالكامل مباشرة. عرف الحقول من الـ GET على نفس الكائن أو introspection.
14. 4 بايت timestamp + 3 machine id + 2 process id + 3 counter = 24 hex.
15. بيكشف الـ schema كله: كل الأنواع والحقول والمعرّفات.

</details>

## 📘 المرحلة 2 — التعمق في IDOR (بعد أسبوع 7)

1. عرّف IDOR بمعادلة من سطر واحد.
2. إيه الفرق بين BOLA و BFLA؟
3. ليه الـ Write IDOR أخطر من الـ Read؟
4. `GET /api/orders/8821` رجّع `403`. اذكر 6 حاجات تجرّبها بعدها.
5. إيه الـ Second-Order IDOR؟ ادّي مثال.
6. إزاي الـ GraphQL aliases بتساعدك في التعداد؟
7. ليه تغيير `Content-Type` ممكن يكسر فحص الصلاحية؟
8. إيه الـ Error-Based Oracle وإزاي تستخدمه؟
9. إزاي تحوّل Read IDOR لـ Critical؟
10. اذكر 4 أسباب برمجية بتخلي الـ IDOR يحصل.
11. إيه دور إضافة Autorize بالضبط؟
12. ليه بنستخدم حسابين في الاختبار؟

<details>
<summary>👈 الإجابات</summary>

1. `IDOR = (معرّف كائن يتحكم فيه المستخدم) × (غياب فحص الملكية)`.
2. BOLA = على مستوى **الكائن** (`/orders/8821`). BFLA = على مستوى **الوظيفة** (`/admin/users`).
3. Read = تسريب. Write = تعديل → ممكن يوصل لتغيير الإيميل → password reset → **ATO = Critical**.
4. تبديل method (POST/PUT/PATCH/DELETE) · `X-Original-URL` · `X-Forwarded-For: 127.0.0.1` · trailing slash / `//` / `;` · `Content-Type` xml/form · تغليف البارامتر · حالة المسار.
5. الوصول بيحصل في طلب **تاني** مش نفس الطلب: أنشئ كائن → اربطه بمكان تاني → اقرأه من هناك.
6. تسمح بآلاف الاستعلامات في request واحد → تعداد المعرّفات وتخطي rate limit.
7. لأن طبقة التحقق/التفويض ممكن تكون مبنية على `application/json` بس.
8. رسايل خطأ مختلفة (403 "Not yours" vs 404 "Not found") = بتأكد وجود الكائن → تعداد.
9. صعّد: Write IDOR → غيّر الإيميل → password reset → ATO.
10. الثقة في العميل · ORM بيخليه سطر واحد · وهم الأمان من UUID · حماية method واحدة بس · إعادة استخدام كود قديم · مفيش اختبارات أمنية.
11. بتعيد كل request تلقائيًا بتوكن منخفض الصلاحية وتقارن النتيجة وتعلّم `Bypassed!`.
12. عشان تقدر تثبت إن **مستخدم تاني** يوصل لبيانات الضحية. بحساب واحد مش هتعرف.

</details>

## 📙 المرحلة 3 — الصيد (بعد أسبوع 12)

1. اذكر 5 معايير من نظام تقييم التارجت.
2. اذكر 3 علامات حمرا تخليك تتجاوز هدف.
3. ليه الـ B2B SaaS أفضل من موقع تسويقي للـ IDOR؟
4. ليه ملفات الـ JS أهم مصدر استطلاع؟
5. UUID غير قابل للتخمين — منين تجيب IDs صالحة؟ اذكر 4 مصادر.
6. إيه الفرق بين تقرير `Informative` و `Accepted` بنفس الثغرة؟
7. اكتب عنوان لتقرير IDOR على `/api/teams/{id}/members`.
8. ليه "عدد المستخدمين المتأثرين" مهم في التقييم؟
9. إيه أول حاجة تعملها لو الـ triager قال `Cannot reproduce`؟
10. إيه أكبر فخ في توزيع الوقت أثناء الصيد؟

<details>
<summary>👈 الإجابات</summary>

1. تعدد المستخدمين · وجود API/موبايل · تعقيد الصلاحيات · اتساع الـ Scope · عمر البرنامج · المكافآت · سرعة Triage · جودة التوثيق.
2. مفيش حسابات مستخدمين · أكتر من 5000 تقرير قديم · مفيش رد لأشهر · مفيش safe harbor.
3. فيه multi-tenancy + أدوار + فرق = كائنات مملوكة وصلاحيات معقدة = مادة خام للـ IDOR.
4. فيها مسارات API وأسماء كائنات وحقول و UUIDs صلبة — أحيانًا تعليقات زي `TODO: add ownership check`.
5. ردود API تانية · القوايم (`/api/teams/{id}/members`) · ملفات JS · الأرشيف · التصدير · رسايل الخطأ · البحث.
6. `Informative` = أثبتّ الوصول بس بدون تأثير. `Accepted` = أثبتّ الوصول **والتأثير** (بيانات حقيقية، عدد متأثرين، ATO).
7. "IDOR on `/api/teams/{id}/members` allows any authenticated user to enumerate all team members' PII across all tenants".
8. لأنه بيحوّل التأثير من "مستخدم واحد" لـ "كل المنصة" = فرق بين Medium و Critical.
9. ابعت خطوات أدق: حسابين تجريبيين، request/response خام، فيديو قصير.
10. قضاء 90% وقت في الاستطلاع و10% في الاختبار. الصح: استطلاع 30% / اختبار 40% / تصعيد 20% / توثيق 10%.

</details>
